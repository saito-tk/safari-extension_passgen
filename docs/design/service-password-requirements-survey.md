# メジャーサービスのパスワード設定条件調査

作成日: 2026-06-22

更新日: 2026-06-22

## 目的

国内で利用機会が多いサービスのパスワード設定条件を調べ、Passgen のプリセット、互換性重視の生成ルール、ヘルプ文言を検討する材料にする。

この文書は実装仕様ではなく調査メモである。サービス側の登録画面やヘルプは頻繁に変わるため、特定サービス向けのプリセットを実装する場合は、その時点で該当サービスの登録/変更画面を再確認する。

## 調査方針

- 公式ヘルプ、公式登録画面、公式アカウント管理画面を一次情報として優先する。
- 検索結果スニペット、第三者ブログ、Q&A、古い画面キャプチャは、サービス候補の洗い出しには使っても、確定条件としては扱わない。
- 文字数上限や利用可能な記号の完全一覧が公開されていないサービスは多い。その場合は「未公開」と記録し、推測で埋めない。
- サービス固有のパスワードルールは、ユーザーが今入力している実際の画面を優先する。
- Chrome で公開登録画面も確認する。ただし、ログイン済み領域、保存済み情報、送信を伴う操作、CAPTCHA、2段階認証の突破は行わない。

## 追加確認メモ

2026-06-22 に Chrome で公開画面の追加確認を行った。

| 対象 | 確認結果 | 反映 |

## 確度

| 確度 | 意味 |
| --- | --- |
| A | 公式ヘルプまたは公式仕様文書に、文字数や文字種が明記されている。 |
| B | 公式登録/変更画面の入力補助やバリデーション文言で確認できる。 |
| C | 公式ページは確認したが、完全な条件は公開されていない。 |
| D | サービス候補としては重要だが、今回の調査では公式条件を確認できていない。 |

## 標準・ベストプラクティス

| 出典 | 要点 | Passgen への示唆 |
| --- | --- | --- |
| [NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html) | 単独パスワードは最小 15 文字、MFA 併用時でも最小 8 文字。最大長は少なくとも 64 文字を許容。ASCII 印字可能文字、スペース、Unicode を受け入れることを推奨。文字種混在の強制はしない。 | Passgen の標準プリセットは長さ重視にする。記号必須を強制しない。 |
| [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) | 8 文字未満は弱い。MFA なしでは 15 文字未満を弱い扱い。最大長は 64 文字以上。全ての文字、Unicode、空白を許容し、無言切り捨てを避ける。 | 互換性プリセットとは別に、強度評価では 15 文字/64 文字の考え方を残す。 |

## 今回の調査から見える傾向

1. 公開情報だけで「使える記号の完全一覧」まで確認できるサービスは少ない。
2. 国内メジャーサービスは、パスワードそのものより、SMS、確認コード、パスキー、生体認証、外部ID連携へ寄っているものが多い。
3. 実利用上の互換性を重視すると、`20文字以内` や `記号制限あり` のサービスを考慮した保守的プリセットが必要になる可能性がある。
4. 一方で、NIST/OWASP 的には短い最大長や文字種制限は望ましくない。標準プリセットをサービス都合に合わせすぎると、強度評価と矛盾する。

## Passgen への設計メモ

現時点では、特定サービス名を冠したプリセットをアプリに組み込むのは避けるべきである。サービス側の仕様変更に追随する責務が重く、誤ったパスワードを生成するリスクがある。

代わりに、次のような汎用プリセット候補を検討する。

| プリセット候補 | 目的 | 例 |
| --- | --- | --- |
| 標準 | 多くの現代サービス向け。長さ重視。 | 20-24 文字、英大小、数字、主要記号。 |
| 記号少なめ | 記号制限が不明なサービス向け。 | 20 文字、英大小、数字、`- _ .` 程度。 |
| 記号なし | 記号で弾かれやすい古いサービス向け。 | 20 文字、英大小、数字。 |
| 短め互換 | 最大 20 文字級のサービス向け。 | 16-20 文字、英大小、数字、必要最小限の記号。 |
| 数字PIN | 公的/決済/端末ロック系の数字入力向け。 | 6-12 桁。通常パスワードとは別扱い。 |

## 実装前に追加で必要な確認

- 主要サービスのうち、実際に登録/変更画面で最大長と記号一覧を表示するものを再調査する。
- 特に `TikTok` のような最大 20 文字級、`Apple Account` のような文字種必須型、`Yahoo! JAPAN` のようなパスワードレス移行型は、プリセット設計への影響が大きい。
- ユーザーが「このサービス向けに生成したい」と選ぶ UI を作る場合は、サービス名ではなく `互換性重視: 20文字以内` のような条件名にする方が保守しやすい。
